# PRD: FrienDiary (talkDiary) — "매일 저녁, 누군가와 통화하듯" 앱

## 1. 배경 / 문제 의식
- 1인 가구·고령화 사회에서는 하루 중 **누군가와 대화할 기회 자체가 적음**.
- 일기를 "직접, 꾸준히" 쓰는 건 귀찮고 부담스러워서 오래가지 못함.
- 그래서 이 앱은 "일기 쓰기"가 아니라, **매일 정해진 시간에 누군가 안부를 물어봐서 자연스럽게 대답하다 보니 그게 기록이 되는** 경험을 만든다.

## 2. 핵심 컨셉
매일 정해진 시간(예: 저녁 10시)이 되면:
1. **전화가 오는 화면**이 먼저 뜬다. (실제 전화 수신 UI처럼 "받기"/"거절" 버튼)
   - 이 화면 자체는 **MVP(Phase 1)부터 포함**된다.
   - 다만 아직 STT/TTS(음성 대화)가 없으므로, "받기"를 눌러도 실제 통화는 아직 일어나지 않는다 — 받든 거절하든 **결국 텍스트 메시지 대화로 이어진다** (받기=바로 채팅 시작, 거절=잠시 후 메시지가 오는 식). 진짜 음성 통화는 Phase 3에서 붙는다.
2. 메시지 대화는 카카오톡처럼, 질문이 오고 사용자가 텍스트로 답하며 이어진다.
3. 대화 내용은 나중에 **대화식**(말풍선, 카톡처럼 주고받은 그대로)으로 볼 수 있다.
   - **일기식(대화 내용을 자연스러운 하루 기록 문단으로 정리)은 AI가 필요하므로 Phase 2로 미룬다 — MVP에는 포함하지 않는다.**

## 3. 질문(대화 시작 멘트) 관리
- 기본 프롬프트(질문)는 미리 설정되어 있음: 예) "뭐해?", "밥 먹었어?", "오늘 별 일 없었어?"
- 사용자가 원하면 문구를 자유롭게 수정/추가/삭제/순서 변경 가능 (기존에 구현된 "질문 설정" 화면 기능을 그대로 계승).

## 4. 단계별 로드맵 (중요 — 범위를 명확히 나눔)

### Phase 1 — MVP: 전화 수신 화면 + 메시지 대화 (지금 구현 대상)
- **전화 오는 화면(받기/거절 UI)은 MVP에 포함.** 단, 이 화면은 겉모습(연출)만 통화이고 실제 음성 통화 기능은 없음.
  - "받기"를 눌러도 → 텍스트 메시지 대화 화면으로 진입 (음성 아님).
  - "거절"하거나 응답 없으면 → 잠시 후 카톡처럼 메시지 알림으로 다시 뜸 → 텍스트 메시지 대화로 진입.
  - 즉 Phase 1에서는 받기/거절 모두 최종적으로 **같은 텍스트 대화**로 이어짐. (받기=바로 시작, 거절=한 박자 늦게 시작 정도의 차이만 있음)
- **AI 없음.** 정해진(또는 사용자가 커스터마이징한) 질문 목록을 순서대로 메시지로 보내고, 사용자가 텍스트로 답하면 그대로 저장.
- 대화 내용을 **말풍선(대화식)** 으로 볼 수 있음.
- **일기식 보기는 MVP에서 제외.** AI 없이 만든 규칙 기반 일기 문단은 이미 품질이 불만족스러움을 확인했으므로, 일기식 보기는 AI가 붙는 Phase 2에서 넣는다.

### Phase 2 — AI 도입 (대화 자연스러움 + 정리)
- AI(Gemini)를 붙여서:
  - 질문-답변을 더 자연스러운 "대화"처럼 주고받을 수 있게(단답이어도 AI가 자연스럽게 리액션하며 다음 질문으로 이어가기 등, 범위는 별도 논의).
  - 하루의 대화 내용을 **일기 형식 문단**으로 정리해서 보여주는 기능 (Phase 1에서 빠졌던 "일기식 보기"가 여기서 추가됨).

### Phase 3 — 실제 음성 대화 (STT/TTS)
- Phase 1~2가 안정화된 후 진행.
- Phase 1에서 만든 "전화 수신 화면"의 "받기" 버튼이 이때부터 **진짜 음성 대화**로 연결됨(TTS로 질문을 말해주고, STT로 사용자 음성 답변을 텍스트로 변환).
- "거절"은 계속 기존처럼 텍스트 메시지 대화로 이어짐(fallback 구조 그대로 유지).

> **범위 원칙**: 매 단계는 이전 단계가 끝나고 검증된 뒤 다음 단계로 넘어간다. Phase 1에서는 전화 수신 화면의 **UI(연출)만** 만들고, AI 호출이나 실제 음성 STT/TTS 로직은 Phase 2/3 전까지 만들지 않는다.

## 5. Phase 1 (MVP) 상세 기능 요구사항

| # | 요구사항 | 설명 |
|---|---|---|
| F1 | 정해진 시각 알림 | 매일 설정된 시간(기본 22:00, 변경 가능)에 로컬 알림 발송 |
| F2 | 전화 수신 화면 (UI만) | 알림 시각에 실제 전화 수신처럼 생긴 화면 표시, "받기"/"거절" 버튼 제공. 음성 기능은 없음 |
| F3 | 받기/거절 → 텍스트 대화로 연결 | "받기"는 즉시, "거절"은 잠시 후 메시지 알림 형태로 텍스트 메시지 대화 화면으로 진입 (Phase 1은 결과적으로 동일한 텍스트 대화) |
| F4 | 메시지 형태 질문 전달 | 커스터마이징된 질문 목록을 순서대로 "메시지 온 것처럼" 한 번에 하나씩 노출 |
| F5 | 텍스트 답변 | 사용자가 카톡 입력창처럼 텍스트로 답하면 다음 질문으로 넘어감 |
| F6 | 대화식 보기 | 그날의 질문/답변을 말풍선(질문=왼쪽, 답변=오른쪽) 대화 형태로 열람 — 기존 구현 재사용 |
| F7 | 질문 커스터마이징 | 기본 질문(뭐해?/밥 먹었어?/오늘 별 일 없었어?)을 유지, 사용자가 수정 가능 — 기존 "질문 설정" 화면 재사용 |
| F8 | 시간 설정 | 사용자가 알림 받을 시각을 직접 설정/변경 가능 |
| F9 | AI 미사용 | 질문 순서 진행, 답변 저장 모두 규칙 기반. 외부 AI 호출 없음 |
| F10 | 일기식 보기 제외 | Phase 1에서는 대화식(말풍선) 보기만 제공, 일기 문단 보기는 Phase 2로 미룸 |

### 결정 필요 (사용자 확인 필요한 부분)
- [ ] 알림을 놓치면(앱을 그날 안 열면) 다음날 어떻게 처리할지 (예: 그냥 다음날 새 대화로 넘어감 / 놓친 날도 나중에 이어서 할 수 있게 할지)
- [ ] "거절" 시 정확히 몇 초/분 후에 메시지가 오는 것으로 연출할지 (즉시 vs 약간의 딜레이)

## 6. 데이터 모델 변화 (기존 대비)
기존 `entries` 컬렉션은 "고정 질문 + 한 번에 답변 모음" 구조였음. 이번 컨셉은 **시간에 따라 순차적으로 진행되는 대화**이므로 구조를 다음과 같이 조정 검토:

```typescript
interface ConversationEntry {
  userName: string;
  dateKey: string;           // 대화가 시작된 날짜
  startedAt: number;
  messages: ConversationMessage[];
  aiParagraph?: string;      // Phase 2에서 채워짐
}

interface ConversationMessage {
  id: string;
  from: 'app' | 'user';      // 질문(app) / 답변(user)
  text: string;
  timestamp: number;
  questionId?: string;       // app 메시지일 때만
}
```
- 기존 `Answer[]` 기반 구조에서 시간순 `messages[]` 구조로 바뀌는 것이 핵심 차이 — 대화가 "질문-답변 쌍의 집합"이 아니라 "순서가 있는 메시지 흐름"이기 때문.

## 7. 기술 스택 / 신규 검토 사항
| 영역 | 기존 | Phase 1에서 추가/변경 |
|---|---|---|
| 알림 | 없음 | `expo-notifications` (로컬 알림, 매일 지정 시각) 신규 도입 |
| 대화 UI | 정적 Q&A 카드 | 카톡 스타일 채팅 화면(순차 메시지 노출) 신규 구현 |
| 질문 커스터마이징 | 있음 (`QuestionSettingsScreen`) | 그대로 재사용 |
| 음성(TTS/녹음/STT) | TTS/녹음 있음, STT 없음 | Phase 1에서는 사용 안 함 (Phase 3에서 실제 통화 기능으로 재도입) |
| AI | 없음 | Phase 1에서는 없음, Phase 2에서 도입 |
| 전화 수신 UI | 없음 | **Phase 1에서 신규 구현** (연출용, 실제 통화 연결 없음) |

## 8. 기존 구현과의 관계 (마이그레이션 관점)
- **재사용 가능**: 로그인/로그아웃, 질문 커스터마이징 화면과 데이터(`users/{name}.questions`), Firestore 연동 구조, 말풍선 UI 스타일.
- **재설계 필요**: "오늘의 기록" 화면(`RecordScreen`)은 정적 Q&A 카드 방식이라, 시간 기반 순차 메시지 방식(채팅 UI)으로 다시 만들어야 함.
- **보류/제거 검토**: 음성 녹음 답변(`VoiceRecorder`), TTS 질문 읽어주기 — Phase 1 범위 밖이라 화면에서 잠시 빠지고 Phase 3에서 다시 사용됨. 코드 자체는 삭제하지 않고 남겨둠.
- **미완성 상태로 둘 것**: 이전에 진행하던 "AI 문장화"(`docs/PRD_ai_sentence.md`) 작업은 이번 로드맵의 **Phase 2**로 흡수됨 — 별도로 먼저 진행하지 않음.

## 9. Phase 1 체크리스트

### 설계/준비
- [ ] "결정 필요" 항목(§5) 사용자와 확정
- [ ] `expo-notifications` 도입 방식 조사 (Expo Go 지원 범위 확인 — SDK54 기준 로컬 알림 가능 여부)
- [ ] 새 데이터 모델(§6) 확정 및 마이그레이션 여부 결정 (기존 `entries` 데이터 유지할지, 새 구조로 갈아탈지)

### 구현
- [ ] 알림 시간 설정 화면/로직 (기본 22:00, 변경 가능)
- [ ] 매일 정해진 시각에 로컬 알림 발송 (`expo-notifications` 스케줄링)
- [ ] **전화 수신 화면(연출용 UI)** 신규 구현 — 받기/거절 버튼
- [ ] 받기 → 즉시 텍스트 채팅 화면 진입 로직
- [ ] 거절/무응답 → 잠시 후 메시지 알림 → 텍스트 채팅 화면 진입 로직
- [ ] 채팅형 대화 화면 신규 구현 (질문이 메시지로 하나씩 오고, 답하면 다음 질문)
- [ ] 대화 저장 로직 (`ConversationEntry`/`ConversationMessage` 구조로 Firestore 저장)
- [ ] "지난 기록"을 대화식(말풍선)으로 보여주는 화면 (기존 UI 재활용)
- [ ] 질문 커스터마이징 화면 연동 확인 (기존 그대로 사용 가능한지 점검)

### 검증
- [ ] 알림이 설정한 시각에 실제로 오는지 실기기 테스트
- [ ] 전화 수신 화면에서 "받기" 눌렀을 때 텍스트 채팅으로 연결되는지 확인
- [ ] "거절"(또는 무응답) 시 이후 메시지 알림 → 텍스트 채팅으로 이어지는지 확인
- [ ] 질문 순서대로 메시지가 오고, 답변 후 다음 질문으로 자연스럽게 넘어가는지 확인
- [ ] 지난 기록에서 그날의 대화가 시간순으로 올바르게 보이는지 확인
- [ ] `npx tsc --noEmit`, `npx expo export --platform android` 통과
